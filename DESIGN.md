# Архитектурное описание (DESIGN.md)

## 1. Overview

Приложение представляет собой сервис для мгновенного поиска информации о странах (столица, регион, население, языки, валюты, границы и флаг). В качестве источника данных используется публичный API countries.dev(`/name/{query}`). Архитектура построена на разделении слоёв: сетевой слой (`SearchService`), слой управления состоянием (`SearchController`), маппинг данных и декларативное обновление DOM.

## 2. Request Cancellation и защита от гонки запросов (Race Conditions)

### Почему `AbortController`, а не boolean флаг актуальности

Простой подход с флагом (`let isLatest = true` или сравнение ID запроса) решает только проблему отрисовки, но оставляет сетевые и ресурсные проблемы:

1. **Лишняя нагрузка на сеть и браузер:** Браузер продолжает скачивать и парсить JSON для устаревших запросов, забивая пул активных соединений (обычно лимит 6 параллельных подключений на домен).
2. **Порядок ответов не гарантирован:** Медленный ответ на первый запрос может прийти позже быстрого ответа на второй. При использовании `AbortController` устаревший запрос физически обрывается на уровне сетевого стека (`fetch`), экономит трафик и гарантирует, что «победит» только последний актуальный запрос.

### Как это реализовано в проекте

Механизм отмены построен как цепочка от пользовательского ввода до сетевого запроса:

- **Мгновенная отмена в контроллере (`SearchController.handleInput` / `runSearch`):**
  На каждый поисковый запрос создаётся собственный экземпляр `AbortController`. Отмена предыдущего запроса происходит **сразу в момент нового ввода** (`handleInput`), не дожидаясь срабатывания таймера `debounce`. Если пользователь уже отправил запрос `'ge'` и начал дописывать `'germany'`, первый запрос обрывается немедленно. В блоке `catch` ошибка `AbortError` перехватывается и тихо игнорируется, чтобы не показывать пользователю ложное сообщение об ошибке сети.
- **Дедупликация и счётчик подписчиков в сервисе (`SearchService.search`):**
  Если несколько компонентов одновременно запрашивают один и тот же `query`, сервис не дублирует сетевой вызов, а возвращает общий in-flight промис. Для каждого вызывающего кода создаётся локальный сигнал и ведётся счётчик активных подписчиков. Если один из подписчиков отменяет свой запрос, счётчик уменьшается, но общий сетевой запрос продолжает жить для остальных. Реальный `abort()` на уходящий `fetch` вызывается только тогда, когда счётчик активных подписчиков падает до нуля.
- **Таймаут запроса:**
  Для защиты от «зависших» соединений пользовательский `AbortSignal` объединяется с таймером через `AbortSignal.any([callerSignal, AbortSignal.timeout(8000)])`. Запрос автоматически оборвётся либо при отмене пользователем, либо по истечении 8 секунд.
- **Доказательство работы:**
  Корректность этой цепочки подтверждена интеграционным тестом в `src/core/tests/search-race.test.ts`, где принудительно симулируется инвертированный порядок ответов сервера и проверяется, что устаревший ответ не перезаписывает актуальное состояние.

## 3. Debounce

- **Выбор задержки (600 мс):**
  Задержка в **600 мс** выбрана как компромисс между отзывчивостью интерфейса и экономией ресурсов:
  - _Если убрать debounce (0 мс):_ На каждую нажатую клавишу улетает отдельный HTTP-запрос. Это создаёт шквал отменённых запросов, нагружает API и засоряет историю поиска неполными обрывками слов (`"g"`, `"ge"`, `"ger"`).
  - _Если сделать задержку слишком большой (например, 1500+ мс):_ Интерфейс начинает ощущаться «тормозным», пользователь не понимает, принят ли его ввод и идёт ли поиск.
- **Почему обёртка создаётся один раз в замыкании:**
  Функция `debouncedSearch` инициализируется один раз в конструкторе `SearchController`. Внутри замыкания хранится идентификатор таймера (`timerId`). Если бы функция `debounce` вызывалась заново внутри `handleInput`, каждый символ создавал бы независимое замыкание со своим таймером, предыдущие таймеры не сбрасывались бы через `clearTimeout`, и все запросы всё равно ушли бы в сеть со сдвигом во времени.

## 4. Сложность алгоритмов (Big O)

- **`mapCountryResponse`:**
  - Для одной страны: **$O(1)$** (константное время). Функция обращается к фиксированному набору полей объекта (`name`, `capital`, `flags`, `currencies`, `languages`, `borders`). Длина массивов валют, языков и граничащих стран у любого государства ограничена небольшими константами (обычно 1–15 элементов), поэтому преобразование выполняется за постоянное число операций.
  - Для массива из $n$ стран: **$O(n)$** (линейное время), так как функция последовательно проходит по каждому элементу входного списка один раз.
- **Кэш результатов (`Map`):**
  - Ключом служит запрос, передаваемый контроллером уже обрезанным `(trim() в SearchController.runSearch)`; Map даёт **$O(1)$** поиск и запись.
- **Дедупликация параллельных запросов (in-flight `Map`):**
  - Проверка наличия уже выполняющегося промиса для текущего `query` и сохранение нового промиса также занимают **$O(1)$**.

## 5. Принципы чистого кода (Clean Code)

1. **Принцип единственной ответственности (SRP один файл = одна роль):**
   - `src/core/map-country.ts` чистая функция трансформации сырого ответа от API в строгую внутреннюю модель приложения без побочных эффектов.
   - `src/core/search-service.ts` инкапсуляция сетевого взаимодействия, кэширования, дедупликации и обработки HTTP-ошибок.
   - `src/core/search-controller.ts` конечный автомат состояний поиска (`idle`, `loading`, `results`, `empty`, `error`), управление таймерами и отменой запросов.
   - `src/core/search-history.ts` изолированная работа с историей поисковых запросов и `localStorage`.
   - `src/ui/` (рендереры и DOM-хелперы) отображение данных и подписка на события интерфейса без знания о том, как устроены `fetch` или кэш.

2. **Strict TypeScript и защита от невалидных данных:**
   В проекте включены строгие проверки компилятора (`strict`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`). Состояния контроллера описаны через размеченное объединение (Discriminated Union `SearchState`), что исключает невозможные состояния интерфейса (например, одновременный показ спиннера загрузки и сообщения об ошибке). Опциональные поля ответа API безопасно нормализуются на границе приложения в маппере.

3. **Декларативный подход к DOM и безопасность:**
   UI выступает чистой проекцией текущего `SearchState`. Обновление списков карточек и истории происходит через `element.replaceChildren(...)` с созданием узлов через `document.createElement`. Использование `innerHTML` полностью исключено, что защищает приложение от XSS-уязвимостей при подстановке данных из внешнего API или пользовательского ввода.
